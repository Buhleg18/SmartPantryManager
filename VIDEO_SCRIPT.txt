[3:30 – 6:00] CONCEPT EXPLANATION (with code open)
Open Android Studio, show the code.

1. STRICT MATCHING (point to DatabaseHelper.getSuggestedRecipes and canMake):
"This is the core business logic. I load the entire pantry into a map of normalised name → total quantity. For each recipe I parse its ingredient string. If any required ingredient is missing or the quantity is too low, the recipe is rejected. Only recipes where every single ingredient is present in enough quantity are returned. Names are lower-cased and trailing ‘s’ is removed so tomato matches tomatoes."

2. RECYCLERVIEW + ADAPTER (point to PantryAdapter):
"The pantry list uses a RecyclerView with a custom Adapter. onCreateViewHolder inflates the card layout, onBindViewHolder fills the name, quantity and optional expiry. When the user taps a card I fire a callback that opens the edit screen with the item id via Intent."

3. INTENTS / NAVIGATION (point to MainActivity):
"Bottom navigation switches between the pantry list and the suggested list inside the same activity. When the user wants to add or edit I start AddEditIngredientActivity with an Intent, optionally putting the id extra. After they save, onResume refreshes the list so the change is visible immediately."

[6:00 – 6:45] DATABASE JUSTIFICATION
"I chose SQLite with SQLiteOpenHelper because the app only needs local, offline storage for one user. It matches what we covered in the module, needs no internet or API keys, and full CRUD plus seeding on first run is straightforward. Data survives app restarts as required."

[6:45 – 7:00] Wrap up
"That covers the GitHub history, a full demo of CRUD and strict matching, the key code concepts, and why I used SQLite. Thank you."
